Appels MCP

browser_snapshot fournit les lignes ci-dessous, puis browser_click utilise la référence reçue. Le compteur passe de 0 à 1 pour chaque variante. Les références sont locales à chaque session. Le script sélectionne la cible : aucun modèle autonome ne décide de l’action.

Avec cursor: default, l’annotation [cursor=pointer] disparaît ; la référence et le clic fonctionnel restent présents dans les trois variantes.

Tests clavier

Le test envoie deux Tab depuis une page neuve, exige le focus sur le bouton, puis active Entrée ou Espace et attend un compteur égal à 1. Deux tests réussissent sur C ; deux échouent sur A et deux sur B, dans chacune des deux séries. Les rapports conservent les huit échecs et les quatre réussites. Les processus des tests A/B terminent avec le code 1.

keyboard.spec.cjs · playwright.config.cjs

Un test en échec peut être le résultat attendu d’une expérience. Il reste un échec du comportement demandé.

Scores Lighthouse

L’alerte de contraste porte sur NOTES, dessiné sur le carnet. Lighthouse rapporte 4,36:1 dans l’original. Après le seul changement de couleur, les trois scores deviennent 100/100 et les barrières clavier de A/B restent observées. L’audit agent-accessibility-tree réussit dans les six rapports ; les deux audits applicables de la catégorie réussissent (arbre d’accessibilité et stabilité de mise en page), tandis que les cinq autres sont non applicables. Ce résultat ne couvre pas le parcours Tab.

Pourquoi 96 pour B et 95 pour C ? L’échec de contraste pèse 7 sur un total applicable de 129 pour A/C. B ajoute quatre audits ARIA réussis, de poids total 28 : (157 − 7) / 157 ≈ 95,54 %, contre (129 − 7) / 129 ≈ 94,57 %. Le score affiché est arrondi.

La prise de focus des contrôles (focusable-controls) figure parmi les contrôles manuels, hors score automatisé.
